# database replication

add more db instance for read traffic and write traffice

master / slave db

master generally write traffic

slave db only read traffic . it get data from master

data-modifying command must be send to master (insert , update , delete)

if all slave DB is down, read traffic temporarily redirect to master

if master goes down, one of slave is promoted to master. But data on the salve might not be up-to-date. running data recoverfy scripts need to be done

# cache

cache can be place in different layer. each layer of cache server can be scaled independently

## read through cache

find exist in cache, serve if exist. fetch resource if not exist. store resource in cache and return back resource

## when to use cache

- data is read frequenyly but modified infrequently
- cache should have time-to-live in the cahce store
- data and cache mismatch when data-modifying operation on data store and cache are not in a single transaction
- single server of cache can be single point of failure. recommend to do multiple cache server across different data centers

## eviction policy

when cahce is full. item added might remove previous cached item

- Least-recently-used (LRU) is the most popular cache eviction policy

least frequenyly used and first in first out policy can be used

# scaling database

can be done by master / slave or sharding

## sharding

sharding key (partition key) is one or more column that determine which DB instance the data belong to.

chooing sharding key that can evenly distributed data

## resharding

when data is unevenly distributed (one db instance serve request more than other). it require updating sharding / hash function and move data around

<Admonition type="tip" title="tip">

Consistent hashing is a commonly used technique to solve this problem.

</Admonition>

## Hotspot key

one shard is being excessive accessed could cause overload. (Celebrity problem)

<Admonition type="note" title="note">

To solve this problem, we may need to allocate a shard for each celebrity. Each shard might even require further partition.

</Admonition>

## Join and de-normalize

JOIN operation is hard to perform on data live in different db instance. a common work around is to de-normalize the database so query can be sone in a single table.

The system design interview simulates real-life problem solving where two co-workers collaborate on an ambiguous problem and come up with a solution that meets their goals. The problem is open-ended, and there is no perfect answer. The final design is less important compared to the work you put in the design process. This allows you to demonstrate your design skill, defend your design choices, and respond to feedback in a constructive manner.



An effective system design interview gives strong signals about a person's ability to collaborate, to work under pressure, and to resolve ambiguity constructively. The ability to ask good questions is also an essential skill


do not jump right in to give a solution. Slow down. Think deeply and ask questions to clarify requirements and assumptions. This is extremely important.

What kind of questions to ask? Ask questions to understand the exact requirements. Here is a list of questions to help you get started:

What specific features are we going to build?

How many users does the product have?

How fast does the company anticipate to scale up? What are the anticipated scales in 3 months, 6 months, and a year?

What is the company’s technology stack? What existing services you might leverage to simplify the design?


Always ask for clarification. Do not assume your assumption is correct.

Understand the requirements of the problem.

There is neither the right answer nor the best answer. A solution designed to solve the problems of a young startup is different from that of an established company with millions of users. Make sure you understand the requirements.

Let the interviewer know what you are thinking. Communicate with your interview.

Suggest multiple approaches if possible.

Once you agree with your interviewer on the blueprint, go into details on each component. Design the most critical components first.

If you get stuck, don't hesitate to ask for hints.

Again, communicate. Don't think in silence.

## things to improve when finalize the system design

Error cases (server failure, network loss, etc.) are interesting to talk about.

Operation issues are worth mentioning. How do you monitor metrics and error logs? How to roll out the system?

How to handle the next scale curve is also an interesting topic. For example, if your current design supports 1 million users, what changes do you need to make to support 10 million users?
